# سياسة الأمان — SECURITY

## النموذج الأمني: المحلي أولاً، والفشل الآمن

هذه المنظومة تعالج **ملكية فكرية مرخّصة وبيانات مهنية حساسة** (كتب طبية، ترجمات، مسارد مهنية). النموذج الأمني مبني على قاعدتين:

### 1. صفر اتصال شبكي

- النواة لا تستورد أي مكتبة شبكات (`requests`, `urllib`, `socket` ممنوعة في مسارات المعالجة).
- نماذج التضمين (ONNX) تُوفر **كملفات محلية** (`model.onnx` + `tokenizer.json`) — لا تنزيل، لا HuggingFace Hub، لا تحديث تلقائي.
- الاختبارات تفشل إن أضاف أي PR استدعاء شبكة (CI يعمل في بيئة معزولة افتراضياً).

### 2. الفشل الآمن (Fail-Closed)

| الحالة | السلوك الإلزامي |
|---|---|
| بيانات تالفة/ناقصة (كتلة بلا صفحة، معرف مشوه، JSON غير صالح) | رفض العنصر + تسجيل BLOCKED في `qa_blocks` + متابعة البقية |
| استثناء داخل محاذاة/مصطلح | العنصر يبقى غير محاذى (UNALIGNED) — لا محاذاة مختلقة |
| حالة غير قانونية في المخطط | رفض من قيد `CHECK` في SQLite |
| ملف مخرجات غير قابل للكتابة | فشل صريح — لا كتابة جزئية صامتة |

**لا تخمين أبداً**: إن لم تكفِ الأدلة لاتخاذ قرار، فالقرار هو BLOCKED ويدخل طابور المراجعة البشرية.

## حماية البيانات

- كل القواعد محلية (`knowledge.db` + `corrections.db`) مع `PRAGMA journal_mode=WAL`.
- `.gitignore` يحظر تتبع: `out/`، قواعد البيانات، TMX/TBX/XLIFF، مجلدات `data/private/` و`models/` — **لا تُرسل ملفات كتب أو مسارد خاصة إلى المستودع أبداً**.
- التقارير HTML مكتفية بذاتها بلا CDN ولا خطوط بعيدة — فتحها لا يصدر أي طلب.

## التعامل مع بيانات الاعتماد

- لا توكنات ولا مفاتيح في الكود أو الملفات أو السجل (git history).
- إن تسرب توكن في Issue/PR: أبلغ فوراً + أبطِله من جهة الإصدار + نظّف السجل إذا لزم.

## الإبلاغ عن ثغرة

افتح Issue بعنوان `[SECURITY]` بتفاصيل كافية لإعادة الإنتاج، دون نشر بيانات حساسة في التقرير نفسه. الإصلاح يتم عبر فرع `fix/security-*` بأولوية قصوى.

## النطاق خارج المسؤولية

أمان نظام التشغيل والقرص ومساحة العمل (أذونات ملفات، تشفير القرص) مسؤولية المستخدم — المنظومة أداة محلية تنفذ بصلاحيات المستخدم الحالي فقط.
